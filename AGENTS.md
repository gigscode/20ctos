# Project guidance

## Writing and language
- Do not use em dashes in app copy, docs, or messages.
- Use plain, warm, human English. Keep words familiar and explain ideas simply.
- Write for people, not engineers. Avoid jargon, made-up terms, inflated claims, and sales pressure.
- Keep the campaign personal, kind, clear, and focused on a real problem and a useful next step.
- The README is for visitors and customers. Keep it welcoming and free of technical setup details.
- Do not describe Olajide with religious or motivational-speaker language.

## Product and accessibility
- Keep the experience mobile friendly, quick, and keyboard accessible.
- Use meaningful labels, visible focus, clear errors, and honest status messages.
- Do not claim a lead was saved or a booking was made unless the server confirms it.
- Do not invent availability, testimonials, client counts, project links, or booking details.
- Collect only details needed to arrange the conversation. Keep marketing permission separate.
- Never send personal answers to analytics.

## Data and security
- Never store form answers in browser storage.
- Never expose private credentials in browser code.
- Validate and limit all submitted data on the server before storage.
- Do not show private submissions without server-side authorization.
- Do not add integrations, environment variables, database migrations, or setup scripts unless the user asks for them.
- If an external service is not connected, explain the limit clearly and do not pretend the feature works.
